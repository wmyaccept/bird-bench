# 什么才算对（EX 判定规范）

<!-- push step=5 -->
## ⚡ 决策速查（提交前的判定口径）
- `set(预测) == set(金标)` ⇒ **列数、列序、行集三者都要精确**：多一列/少一列/换顺序都是 0 分。
- 加不加 `DISTINCT` **不影响判定**（重复行被 set 折叠），但也别用 DISTINCT 掩盖行集错误。
- `ORDER BY` 不影响判定，只在并列时决定 `LIMIT 1` 取到哪一行。
- 浮点顺序会影响判定：`CAST(x AS REAL) * 100 / n` 与 `CAST(x AS REAL) / n * 100` 末位可能不同。
<!-- /push -->

判分依据是 BIRD 官方的 `evaluation_ex.py` / `evaluation_utils.py`，核心只有一行：

```python
res = 1 if set(predicted_res) == set(ground_truth_res) else 0
```

`fetchall()` 出来的是**元组列表**，所以：

| 影响判定 | 不影响判定 |
|---|---|
| 每一行的**值的集合** | 列名、别名 |
| 每一行内部**列的顺序**（元组按位置比） | `ORDER BY`（集合无序） |
| 列的个数 | 重复行（`set()` 会把重复折叠掉） |

## 三条容易搞错的推论

1. **列顺序真的会影响判定。**
   `SELECT a, b` 和 `SELECT b, a` 是两个不同的结果集。题目按什么顺序问，就按什么顺序 `SELECT`。
2. **加不加 `DISTINCT` 不影响 EX**（重复行被 `set()` 折叠），
   但**漏掉任何一个不同的值一定错**。别在 `DISTINCT` 上纠结，要纠结"值集合是不是完整"。
3. **`ORDER BY` 只在并列时决定 `LIMIT 1` 取到哪一行**，不影响集合本身。

## 由此衍生的两条实用推论

<!-- canon:shape-after-submit  只指路，不重复声明（唯一出处：diagnosis.md） -->
> ⛔ 下面两条推论里的"金标 N 行"同样**只有提交之后**才看得到，用途是喂给**后续**同库题，
> 不是回头改那道已看过金标的题。完整前提见 `diagnosis.md` 的「行数 / 列数反推手册」。

- **金标行数 ≠ 不同值个数。** 金标 15 行可能只有 12 个不同值。反过来，
  如果我的结果有 N 个不同值，而金标有 M 行（M < N），那两个集合一定不相等。
  **用"含重复行的行数"能反推"不同值的个数下限"**——`casebook.md` 里 `idx 205` 就是靠这个排除的。
- **判断"该返回哪一列"时，可以算不同值个数。**
  金标 N 行，某候选列只有 M 个不同值（M < N）⇒ 那一列不可能是金标的输出列。
  实测 `idx 346`：金标 25061 行，`cards.name` 只有 17544 个不同值 ⇒ 金标返回的是 `cards.id`。

## 配套口径（`bird.py score`）

- 每题的判定与官方 `execute_sql` + `calculate_ex` 完全一致（已交叉验证 110 题逐题一致）。
- 报告分三个维度：总分、分难度（simple/moderate/challenging）、分数据库。
- **两个口径要分清**：
  - `EX = 正确数 / 已作答数` ← 默认显示，衡量"做过的题里对了多少"
  - `全量 EX = 正确数 / 500` ← 跑官方脚本时的口径，未作答按错计
- 逐题明细在 `work/score/score_report.json`，含每题失败原因（detail）。
