# 定稿前自检清单 + 反模式 + 效率纪律

## 提交前逐条过一遍

这几条能挡掉大部分"看起来对但 EX=0"的情况：

- [ ] evidence 里的每一个口径都在 SQL 里体现了吗？
- [ ] 结果集是空的吗？空结果通常是 JOIN 条件写错或值匹配失败（大小写/格式/NULL）。
- [ ] **行数**合理吗？题目问"哪个 X"却返回 100 行，多半缺 `LIMIT 1` 或少了聚合；
  反过来只返回 1 行，但金标可能是并列全返回（见 `gold-style.md` 第 2 条）。
- [ ] **列数和列顺序**对得上题意吗？"年龄和名字"这种问法，列顺序按问的顺序排。
- [ ] 题目说"比率/百分比"了吗？有没有忘 `CAST AS FLOAT`，比率方向有没有搞反？
  **分母是行数还是去重实体数**？先按行数试（见 `calibration.md`）。
- [ ] 涉及"某月的总量/某年的最高月值"吗？先想清楚**聚合层级**：取单行的极值，
  还是"先按时间分组汇总、再取极值"？（见 `calibration.md`）
- [ ] 涉及"最大/最小/最好"的列**有 NULL 吗**？金标可能把 NULL 当成最小值（见 `gold-style.md` 第 3 条）。
- [ ] JOIN 的键选对了吗？（`id` vs `player_api_id` vs `team_api_id` 这类双 ID 陷阱）
- [ ] 日期/年份是字符串吗？用 `SUBSTR` 还是 `STRFTIME`，别用 `YEAR()`（见 `sqlite-and-data.md`）。
- [ ] 题干里绕口的限定条件，是"金标一定实现"还是"金标可能没实现"？行数不对时先去掉试试。
  **特别是那些靠语意推断、没有对应列的限定词**（"entrusted to manage the budget"、"not fundraisers"）。
- [ ] ⚠️ **题干里有“某年/某月的 X” + “最…/多…/少…”吗？**
  先问：“X 是不是该先按实体（客户/学校/球员）汇总再取极值？”（`idx 1`、`idx 13` 都栽在这里）
- [ ] "all the X who ... give their Y" 这种问法：金标往往是**行级输出**——
  不要 `DISTINCT`、也不要顺带把 X 的 id 选出来（`idx 29`）。
- [ ] 条件里用到的列，**在正确的表上吗**？（见 `naming-traps.md`）
- [ ] evidence 里的数字和题干矛盾吗？矛盾时以**题干**为准，但 evidence 里的列名仍是线索。
- [ ] 列数比题面概念多吗？多出来的那列先试**主键 id**，再试**窗口函数的名次列**（`gold-style.md`）。

## 反模式（不要做）

- **不要**为了拿答案去读 `data/MINIDEV/mini_dev_sqlite.json` 或 `mini_dev_sqlite_gold.sql`，
  也不要 `bird_question --reveal`（**唯一例外**：一批题做完后的复盘，见 `casebook.md`）。
- **不要**为了凑形状，把复盘时看到的金标 SQL 拼回 `answers.json`——那 EX 就变成对答案的拟合了。
- **不要**一次读完整个库的全部列（`bird_schema` 无 `table` 时故意只给列名，就是为了防止这个）。
- **不要**把 `bird_query` 的输出当成最终答案直接提交；它是验证手段，不是解题过程本身。
- **不要**在 SQL 里写 `DROP/UPDATE/DELETE/INSERT`——工具层会拒绝，这是故意的。
- **不要**一题失败就在同一思路上微调十次。先看 detail 属于哪一类错因（见 `diagnosis.md`）。
- **不要**把 `question_id` 当题号用（500 题里没有一个 `question_id` 等于它的下标）。

## 效率与并发纪律

- ⚠️ **同一题不要试第 3 种写法。** skill 写明“先试 A、不行改 B”的照做；B 也不行就
  **提交 B**、记进挂起清单、做下一题。现场穷举候选是效率杀手，而且几乎不会提高正确率 ——
  正确的修法是把根因写回 `references/`，下次同类题一次做对。
  （完整规则见 `SKILL.md` 硬规则第 6 条：“做题时不许思考，思考只在复盘时”。）
- ⚠️ **不要把 `bird_answer` 和 `bird_score` 放在同一批并发调用里。**
  `bird_score` 读的是答案文件，并发时可能读到**写入前的旧答案**，你会看到一个过期的失败结果，
  然后基于它做出错误判断。（本项目真的踩过：差一点把已经做对的 `idx 205` 当成金标缺陷。）
  正确顺序：先 `bird_answer`（多个可并发），**等它返回**，再 `bird_score`。
- **同一个库的题连着做**：`bird_list --db <db_id> --limit 30`，schema 认知可以跨题复用。
- **一批 5–10 题一起提交**（工具层有文件锁，并发安全），再跑一次 `bird_score`，
  比一题一评分省掉大量往返。
- **每 10–20 题按错因分类记录**：是"值集合差一个"还是"行数差一截"？
  前者是口径问题，后者是条件问题。分类比记住具体题目有用得多。
- `work/score/score_report.json` 里有逐题 detail，可以直接筛出所有"行数不同"的题集中处理。
